# Adventurer's Tome v1.6.0-qa.11 — Contextual Relations Consumer

**Baseline:** v1.6.0-qa.10  
**Verified Foundry baseline:** V13.351

## Goal

Consume the generic campaign relationship graph directly in Tome character/profile Relations panels.

This is a presentation consumer. It does not own or rewrite the source system's relationship data.

## Behavior

For the active Actor profile, Tome now merges:

- existing manually-authored Tome relations
- discovered semantic graph relationships

Manual Tome relations remain preserved.

Semantic relations are resolved in this order:

1. canonical linked Actor, if readable
2. projected Tome Contact Journal, if readable
3. read-only semantic fallback card

## Presentation

A semantic relation may show:

- target name
- normalized role
- relationship status
- origin
- profession
- culture
- location
- source badge

Navigation:

- linked Actor → open Tome character profile
- semantic-only projected Contact → open Tome World Contact
- non-materialized semantic fallback → non-clickable card

## System independence

The Relations consumer reads only:

- `module.api.discovery.relationshipsFor()`
- `module.api.discovery.get()`
- `module.api.contactProjections.list()`

It does not branch on Realm Guard or call any system API directly.

## Duplicate behavior

Manual relations render first.

Semantic rows are deduplicated conservatively against already-rendered relation identities.

Name alone is not canonical identity.

## Permission boundary

The consumer uses already permission-filtered Discovery results and requires readable Actor/Contact targets before navigation.

It must not reveal a hidden target through the profile UI.

## QA A — known Realm Guard profile

Open a character with known Social Network relationships.

Expected Relations panel:

- is populated automatically
- shows one row/card per discovered relation
- role/status/origin context is visible
- semantic-only Contacts navigate to World Contacts
- Actor-linked relations navigate to character profiles

## QA B — no manual duplication

If a manual Tome relation represents the same target/role already shown:

- only one equivalent row should render
- manual relation presentation wins

## QA C — semantic-only target

Use a Contact with no Actor.

Expected:

- relation appears
- Contact name/role appears
- clicking opens its Tome World Contact projection
- no Foundry NPC is created

## QA D — linked Actor target

Use a relation with canonical Actor UUID.

Expected:

- relation appears
- navigation opens the Actor profile
- no duplicate Contact/Actor row for the same semantic identity

## QA E — live refresh

Change relation data/source state.

Expected:

- Discovery refresh triggers Tome refresh
- Contact Projection refresh triggers Tome refresh
- open profile updates without manual reload

## QA F — player visibility

On a real player:

- only readable source relationships appear
- hidden Actors/Contacts do not become navigable leaks
- GM-only/private semantic sources remain absent
