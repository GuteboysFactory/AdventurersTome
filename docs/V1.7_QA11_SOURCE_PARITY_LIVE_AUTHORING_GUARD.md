# v1.7.0-qa.11 — Source Parity Live-Authoring Render Guard

**Baseline:** v1.7.0-qa.10  
**Foundry baseline:** V13.351  
**Scope:** block the verified legacy Source Parity full-Tome render while a Tome editor is active.

## Verified root cause

Runtime trace on qa.10 showed:

```text
updateJournalEntryPage
→ adventurersTomeUniversalRegistryRebuilt
→ APP RENDER while:
     _bulkUpdating = true
     _atRichEditingCount = 1
→ FOCUS OUT
→ active authoring DOM removed
```

The legacy `foundry-source-parity.js` module registered:

```js
for (const h of [
  "createJournalEntryPage",
  "updateJournalEntryPage",
  "deleteJournalEntryPage"
]) Hooks.on(h, atpScheduleRender);
```

and `atpScheduleRender()` performed its own unconditional full Tome main render after 100 ms. This bypassed the newer central background-refresh guard.

## Fix

Source Parity now:

- detects `_bulkUpdating`
- detects `_atRichEditingCount > 0`
- detects supported live Tome editor DOM states as a fallback
- marks its refresh pending instead of rendering while authoring is active
- resumes one pending render only after authoring has ended / save state has settled

No Source Parity data synchronization is disabled.

## QA — Session Chronicle

1. Open a Session Chronicle.
2. Type continuously through at least 3–4 autosaves.
3. Pause between autosaves and continue without clicking the editor again.

Expected:

- autosave continues
- caret remains
- focus remains
- editor remains active
- no full Tome jump
- no active authoring DOM removal

Then deliberately click outside.

Expected:

- editor closes normally
- one deferred Source Parity refresh may occur
- saved text remains intact
