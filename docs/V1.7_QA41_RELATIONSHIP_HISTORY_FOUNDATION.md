## Architecture

qa.40 identity resolution remains the authority. A new module consumes existing canonical entities and source-specific resolved Memory mentions. It reads Session/Quest pages, saves attributed relationship evidence and derives profile state/backlinks. It never creates an entity, writes a second Actor/Contact, edits a campaign profile or changes canonical source links.

Relationship evidence and GM decision history are persisted as additive data in a hidden user-scoped setting, following the existing GM Memory storage model. There is no additional administrative Journal tree. Evidence survives edits/deletions as retired history. Decisions are appended separately; confirming/rejecting does not change the original source claim. Sync and decisions use one serialized write queue; only the active GM automatically persists extraction.

## Evidence model

Each row carries a stable evidence ID, canonical relationship key, subject UUID, relation type, object UUID, source Journal/Page UUIDs, source kind/name/excerpt/offset, rule provenance, confidence, source-bounded visibility, existing Session number and presentation sort, and current source-presence marker. Semantics are separate: `polarity` (positive/negative), `certainty` (asserted/possible/rumoured/disputed/unknown), `temporalScope` (current/historical/unknown), and optional `changeSemantics` (no_longer/former/changed). The original extractor `status` is retained for compatibility, not used as the state engine's temporal truth. Relation keys include canonical endpoints and type; symmetric friend/acquaintance endpoints are normalized. Excerpts and provenance remain attributed to their original source. Sort and extraction order do not establish narrative chronology.

Multiple sources/claims contribute to the same relationship. For opposite supported claims, an existing numeric Session chronology may identify the latest state. Unknown chronology, mixed source kinds or contradictions at the same Session number remain conflicting. Old friendship and a later lack of trust are separate relation types; the latter never invents an end to friendship.

## qa.41 semantic-state correction

Root cause: the initial resolver treated all asserted evidence as current and used one negative bucket/positive predicate label for both denial and cessation. Extraction did not emit temporal semantics. This conflated evidence certainty with narrative time.

Final flow: SOURCE/PROVIDER → normalized assertion (`atReNormalize`) → additive evidence store (`atReIngest`/`atReSync`) → semantic resolution (`atReSemantic`/`atReResolution`) → registry presentation (`atRePresentation`) → Tome profiles and inverse backlinks. The resolver/store/presentation do not parse English. Only `atReExtract` is the bounded English provider. There are no QA campaign identity names or full fixture sentence switches in production relationship logic.

### Provider contract

`game.modules.get("adventurers-tome").api.campaignRelationshipEvidence.ingest(providerId, assertions)` accepts structured assertions directly, without invoking the English extractor. Supply canonical `subjectUuid`, `relationType` (or `predicate`), `objectUuid`, polarity, certainty, temporalScope, optional changeSemantics, sourceUuid/reference/page, sourceKind, sourceExcerpt, chronology only if known, confidence, privacy/visibility and provenance. Registry predicates are the supported semantic vocabulary. Use a stable providerId and optional assertionId. Missing semantic information defaults conservatively to unknown; registered predicates, distinct canonical endpoints and real source references are validated. Repeated identical assertions are idempotent; a changed claim appends evidence rather than replacing an earlier claim. Source deletion retires provider evidence during sync. Providers must supply genuinely supported claims; they are trusted GM-only inputs, not arbitrary player writes.

The GM ledger continues to be private per user. Imported/provider evidence is not published to players by this contract. Player reads continue fresh derivation from viewer-visible source pages and canonical links. Future player-facing providers need an explicit viewer-visible evidence delivery path; they must not read the private GM ledger.

### Resolution, decisions and presentation

- Historical-only evidence yields Historical, never Current. Unknown temporal support yields Unknown rather than invented current truth.
- Explicit present support may establish Current alongside older historical evidence. Later explicit no_longer/former changes can supersede earlier current support only with actual comparable Session chronology; contradictory claims with unknown order remain conflicting.
- Plain negative membership is Not a member / Denied / negated. It never implies former membership. Explicit no_longer is labelled No longer; explicit former is Historical / Former.
- Historical information supply stays Historical. Temporal markers are scoped to the attached relation clause, so past information supply cannot move a separate present membership denial into the past.
- Same-session contradictions and undated opposite-polarity support remain uncertain/conflicting. No history is overwritten or narrative dates invented.
- The `ATRE_REGISTRY` mapping supplies forward, inverse and negative labels and symmetric key behavior; `atRePresentation` adds temporal/certainty labels. Forward and inverse profiles resolve the same rows. Profile history displays semantic labels too.
- GM confirm overrides uncertain certainty, not polarity or historical/unknown temporal scope. Possible/reject/unresolved remain append-only decisions and cannot manufacture present support.

### Compatibility

The setting key stays `campaignRelationshipEvidenceV1`; new writes use schema version 2. Legacy status can safely imply polarity/certainty or explicit ended/no_longer, but missing temporal information remains unknown. Normalization on read does not persist changes. Sync/ingestion/decisions retain raw old row fields; no destructive migration or history wipe is performed. Re-extracted evidence with the same stable ID receives the new provider semantics and retains its existing decision history.

## Extraction rules

### Assertion-scoped temporal correction (after `3bc9a0796b195bdf9f09173b5ea31ae68d4ebcfc`)

Root cause: past verb forms (especially owed/recognized) could override an explicit continuing cue, and some evidence keys represented a whole sentence rather than its distinct propositions. A historical encounter was also treated as a historical-only knowledge relationship.

`atReEnglishClause` bounds each predicate/object proposition by conjunctions or semicolons outside resolved entity names. It retains that source span and supplies only its own prefix/suffix to `atReEnglishTemporal`. Canonical names are masked before temporal cue matching. This is conservative English-provider logic, not a general NLP parser. Named or uniquely established object pronouns may be reused; ambiguous references are not guessed. Safe subject/pronoun restrictions from the previous foundation remain.

Assertion-local still/currently/presently/now/remains/continues cues override past verb morphology. Explicit no_longer keeps current negative/change semantics. Historical cues such as formerly/previously/once/used to/in the past/years ago/earlier journey apply only to the relevant proposition. Explicit copulas, present verbs and existing nominal roles supply current support; otherwise the provider may emit Unknown.

Recognition from an earlier journey now emits KNOWS with `temporalScope: unknown` and `eventTemporalScope: historical`: the encounter is historical, but that does not establish that knowledge ended. Explicit MET is historical event evidence, distinct from a continuing relationship. The registry adds bounded SERVES, MET, SPEAKS_WITH and INFORMATION_PROVIDER predicates; bare past information supply does not invent an informant occupation.

Every extracted row retains its full `sourceExcerpt` and additionally carries `sourceSpan: {start, end, text, coordinateSpace: "plain-text"}`. Offsets refer to the extracted plain page text, not raw HTML; blank lines and leading whitespace are accounted for. Compound information claims retain their separate role provenance and information clause span.

Established first-assertion IDs stay compatible with existing GM decisions. Further distinct same-predicate propositions in one sentence receive separate stable span-based IDs, so historical/current claims cannot silently overwrite each other. Repeated extraction/reload is idempotent. Direct provider IDs now distinguish spans; matching already persisted legacy provider IDs/spans retain their decision history on re-ingestion. No destructive migration occurs.

The engine still receives normalized assertions only; English cue processing is isolated to the provider helpers. `ingest(providerId, assertions)` preserves an external provider's `sourceSpan` and temporal fields without parsing its text. Canonical identity, viewer-visible player derivation, private GM decisions and Session Chronicle cleanup remain intact.

## Profile and Review behavior

Actor and World profiles show a compact Relationships section from structured state, including canonical navigation, readable state, evidence count and expandable attributed history/source links. Reverse labels include friend, acquaintance, quartermaster, commander, keeper, member, informant, base for, known by and owed a favour by. No reverse evidence copy is written.

Possible relationship evidence appears in existing Campaign Tools → Analysis with source focus. GM actions: Confirm relationship, Keep as possible/rumour, Reject, Leave unresolved. Rejected claims remain in history and are labelled rejected. An accepted possible/rumour leaves the pending queue without becoming a hard fact. Session/Quest keep only the existing GM Review indicator, which includes pending relationship decisions.

Expanded Session detail no longer renders Chronicle excerpt/bodyPreview. List-card previews, the full Journal/Chronicle viewer, data and Quest presentation remain. The field itself is not deleted.

## Privacy

The GM ledger and decisions are user-private. Player API reads never access the GM ledger. Players derive only presently explicit claims from presently observable sources/pages and observable canonical endpoints already linked by that source. They do not substitute a visible namesake for a hidden canonical endpoint. Both Foundry OBSERVER permission and existing Tome canView/GM-only/Undiscovered controls are checked at read time. GM aliases/profile secrets and GM-confirmed rumours are not used in player derivation. Hidden or deleted evidence cannot contribute to a player's output. Public negative evidence is included in derivation so an earlier positive claim cannot incorrectly stay current. Profiles show only supported current relationships to players; GM sees uncertain/conflicting/negative/history states.

## Limits / stop point

- This is bounded explicit-pattern extraction, not general language understanding. Unsupported or ambiguous references remain diagnostics/identity review; no graph/timeline/story interpretation is added.
- First-name/pronoun handling is conservative and paragraph-bound. A second identified person prevents automatic attribution of the following He/She. No cross-source/global short-name identity merge occurs.
- Existing manual Actor relations are retained separately; this foundation does not rewrite profile authoring or publish a shared relationship registry.
- GM evidence/decisions follow existing user-private Memory storage; no automatic cross-GM history/decision sharing. Player derivation is read-time and limited to currently available source evidence, not private GM history.
- Conflicting explicit evidence is visibly labelled in profiles/history; this foundation does not implement a separate conflict-resolution wizard.
- Confidence is rule evidence, not a guarantee of narrative truth. Source claims remain attributed.
- Live Foundry visual and multi-client QA is pending Per.
