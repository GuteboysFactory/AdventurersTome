## Entity intelligence and backlinks

`game.modules.get('adventurers-tome').api.entityIntelligence.profile(uuid)` returns a detached viewer-safe model:

- canonical `entity` identity/category;
- flat `relationships`: visible first-class rows from the same normalized graph;
- `connectionGroups`: Current, Historical, Possible/uncertain, Denied/negated;
- `relatedGroups`: category-grouped contextual navigation to distinct canonical relationship targets; separate predicates remain distinct Relationships rows;
- `context`: deduplicated presentation rows, internal visible connection reasons, unique count, disjoint appearance/relationship/link groups and category-coalesced `navigationGroups` for the compact Related section; the source `appearanceGroups`, `relatedGroups` and `linkGroups` remain intact;
- each relation retains its exact qa.41 semantic state, predicate, inverse direction, polarity, certainty, temporal scope, history and evidence count;
- `appearanceGroups`: visible Sessions, Quests and Lore/Journal sources;
- `linkGroups`: visible existing canonical/legacy Campaign Links, grouped by generic category;
- optional `enrichment.label`.

Unknown remains Unknown. Conflicting stays conflicting. Negative relationships never enter Current connections; historical negative predicates remain negative. Both endpoints project the same underlying evidence, with inverse predicate labels. UUID maps deduplicate repeated references and proven projections; names never identify or merge entities.

Generic categories cover people, organizations, locations, items, sessions, quests, narrative sources and scenes. Explicit `entityCategory`/semantic category metadata also supports future document categories. Standard Foundry UUID resolution permits other document classes without a system adapter. World profile categories take precedence over the generic World flag; singular/plural source flags and the existing folder-based source classification are supported.

## Why connected and sources

Relationships shows each target, natural predicate, semantic state and evidence count without expanding Context. Each row has two sibling disclosures: Why connected? shows the relevant source title, excerpt, count, provenance and exact-source action; Relationship history / sources lists all supporting assertions. Both use the same viewer-scoped evidence model. Full original provenance and source span remain in the model.

Open source resolves the canonical source UUID and exact page UUID. Source pages open in the native Journal with the specified page selected; source links without a page open the matching Tome Session/Quest/profile. Deleted/mismatched/unavailable pages cannot silently open another page. GM history explicitly marks missing sources/pages; a deleted source no longer supplies Current support. Players receive only a generic unavailable outcome, without revealing whether an inaccessible source exists.

## Navigation

Actor and Journal links use the existing Tome `_openRefKey` and bounded `_navigationHistory`. Generic Items/Scenes/other document classes use the compact Tome entity-context view. `activeContextUuid` is captured and restored by the same Back flow. Session context also has Back when history is present. No browser URL history or new router is introduced.

## Viewer-scoped privacy

The graph boundary filters source/page and canonical endpoint visibility before grouping, semantic resolution and evidence counting. Players call qa.41's fresh visible-source extraction, never the GM evidence/decision ledger. Intelligence indexes only visible documents and supported graph edges; no hidden-category rows, hidden counts, missing-private-source indicators or navigation suggestions are computed for players. Aggregate Campaign Link flags from mixed/private-page Journals are excluded for players because those flags lack per-page provenance; independently visible relationship evidence remains supported. Cache identity includes viewer ID/GM role; document/page/permission/access/setting and campaign-change hooks invalidate it.

## Adapter boundary and no-adapter behavior

Realm Guard is **not a Core dependency**. Neither Genesys nor any other system is required. Core does not access `game.system`, system Actor types or system rules.

Optional integrations may call `entityIntelligence.registerEnricher(fn)`. A synchronous provider receives a detached viewer-visible entity/relationships/links model and may return `{label: '...'}` for escaped display text. It must honor the viewer boundary and must not fetch hidden campaign facts. It cannot change canonical IDs, graph state, grouping or truth. Missing, throwing or asynchronous enrichers fall back to normal Core presentation. Tests exercise no adapter, the real Realm Guard and Genesys adapter registrations, separate Realm Guard-labelled/Genesys-labelled/mock enrichment and failure fallback. Live cross-system Foundry QA remains separate from these automated registration/presentation tests.

## Index and performance strategy

One graph derivation and one visible-document pass build UUID adjacency maps per invalidation. Repeated profile queries read the relevant adjacency rather than scanning the world or extracting sources again. Results and adapter inputs are detached copies. A 220-relation fixture queried 50 times verifies one graph build; explicit invalidation rebuilds from canonical data. Ordinary recent-navigation/window preference writes do not invalidate the index; relevant evidence settings and campaign/permission/document hooks do. No index writes or render hooks are used, avoiding render/update feedback loops.

## qa.42 cross-group Context deduplication hotfix

Root cause: `atEiIndex` legitimately retained appearances and Campaign Links independently, and `atEiProfile` grouped each source independently via `atEiGroups`. `entityContext` then rendered both arrays verbatim. Maps deduplicated within each source, but there was no composed presentation merge. The same canonical Session could therefore be rendered twice; relationship-target navigation could overlap too. This is a projection/composition issue, not an identity or graph-resolution issue.

`atEiContext(related, links, appearances)` now merges these already canonical, viewer-filtered rows by UUID. It preserves visible causes `APPEARS_IN`, `RELATIONSHIP` and `CAMPAIGN_LINK`, their labels and booleans on each merged row. `context.rows` and `context.count` describe unique entities; presentation groups are disjoint with priority Appears in → relationship-target navigation → additional Campaign Links. Original source groups, link flags and evidence remain intact. Different UUIDs retain separate rows regardless of identical names/categories. The rule is category-independent, including future categories.

The `entityContextRow` inline partial renders one canonical target button and expandable Connection reasons. `entityContext` renders the merged groups instead of raw groups. The Relationships section, its Why connected/history and the separate GM Mentioned In remain unchanged. Relationships may reference the same target independently because these are assertions, not Context navigation rows.

GM link management still mounts in Campaign Links. `atCelManagerForActor` searches the entire Context section for existing Session/Quest buttons and attaches the existing unlink action to the surviving row; it marks that scope for the existing event delegation and reset cleanup. It does not add another entity button, and player rendering does not mount this manager.

Privacy correction: aggregate link flags have no per-page occurrence provenance. `atEiVisibleAggregate` is used by `atEiIndex` for both directions of flag-derived source appearances, preventing an independent public link from inventing a hidden-page occurrence cause. A public link may remain without an Appears in cause. Independently visible relationship evidence can still support Appears in, while a hidden aggregate Campaign Link contributes no additional reason/count. Merging occurs after these visibility boundaries; enrichers receive detached data and cannot change the causes or truth.
