# Adventurer's Tome v1.6.0-qa.15 — Privacy Authority Consolidation

**Baseline:** v1.6.0-qa.14  
**Verified Foundry baseline:** V13.351

## Why qa.15 exists

qa.13 and qa.14 treated symptoms on different consumer surfaces. Live QA proved the real problem was architectural:

- generated Contact Journal ownership could become stale
- an inferred "manual override" state could freeze that stale ownership
- downstream consumers then disagreed about whether the same derived Contact was visible
- Discovery could still retain adapter-derived relationships to canonical Actors the current viewer could not observe

The result was repeated surface-specific privacy patches instead of one authority model.

qa.15 consolidates privacy authority so there is one rule:

> Derived semantic data may only exist for a viewer when the evidence supporting it is visible to that viewer.

## Changes

### 1. Evidence authority outranks projection ownership

For automatic semantic Contacts, `ownershipManaged` no longer acts as a visibility bypass.

A generated Contact remains viewer-visible only when its supporting Actor evidence is currently observable.

This applies even if the Contact Journal itself still has broader/stale Foundry ownership.

### 2. Generated ownership stays generated

The old heuristic interpreted any Journal ownership signature mismatch as a permanent GM override.

That was unsafe because ordinary Foundry ownership changes could freeze stale broad Contact permissions.

qa.15 removes that inference.

Generated Contact ownership remains managed unless an explicit future `permissionOverride:true` flag exists.

### 3. Effective Foundry ownership calculation

Negative/inherit ownership values are resolved through the document default before intersection.

This avoids invalid or misleading permission intersections.

### 4. Discovery filters hidden canonical evidence

Universal Campaign Discovery now removes adapter entities and relationships whose canonical Foundry endpoint exists but is unreadable to the current viewer.

This is generic Core behavior, not Realm Guard-specific logic.

Consequences:

- hidden canonical Actors do not survive as adapter-derived semantic entities
- relationships to those hidden canonical Actors do not survive in the viewer-scoped Discovery graph
- downstream projections and Campaign Graph consumers start from filtered evidence instead of filtering after derivation

### 5. Foundry Link is GM-only

Canonical Actor UUID facts are implementation metadata.

Generated `Foundry Link` facts are now GM-only even when the Contact itself is visible.

### 6. Permission audit

`game.modules.get("adventurers-tome").api.contactProjections.permissionAudit()`

GM-only audit reports any generated Contact Journal that a player can observe while the required Actor evidence is not observable.

`contactProjections.audit()` includes this result and fails health when such violations exist.

## QA protocol

### A. Current regression — Baran Dev

Setup:

- Dev Player can observe Dev Testsson
- Dev Player cannot observe Actor Baran Dev
- Dev Testsson has a semantic/link relationship to Baran Dev

Expected as Dev Player:

1. Dev Testsson → Relations: Baran Dev absent
2. World → Contacts: Baran Dev absent
3. Campaign Explorer → Contacts: Baran Dev absent
4. Contact category count excludes Baran Dev
5. Search for Baran Dev: no result
6. stale direct navigation/profile route: profile does not render
7. no Actor UUID / Foundry Link leakage

Expected as GM:

- Baran Dev remains visible
- Contact remains linked and functional

### B. Testas Testasson

Repeat the same privacy expectation for Testas Testasson if that Actor is also unreadable to Dev Player.

### C. Same-name identity regression

Both readable Gunther Contacts remain separate.

### D. Audit

As GM run:

```js
game.modules.get("adventurers-tome").api.contactProjections.permissionAudit()
```

Expected:

```js
{
  healthy: true,
  violations: []
}
```

Then run:

```js
game.modules.get("adventurers-tome").api.contactProjections.audit()
```

Expected: `healthy: true`.

### E. Reload/lifecycle

- reload GM
- reload player
- change Actor ownership once
- verify Contact visibility follows without creating duplicates
- no recurring console errors

## Promotion rule

Do not add another surface-specific privacy patch if this QA fails.

If qa.15 still leaks a derived Contact, diagnose the evidence source and permission graph before changing a consumer UI.
