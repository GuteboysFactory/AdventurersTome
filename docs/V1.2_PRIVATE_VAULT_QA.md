# Adventurer's Tome v1.2.x — Foundry Source Parity I + Contextual Private Vault QA

## Build under test

- `v1.2.0-qa.2`
- Stable regression baseline: `v1.1.15`
- Previous QA baseline: `v1.2.0-qa.1`
- Foundry baseline: `13.351`

## Scope of qa.2

`v1.2.0-qa.2` keeps the qa.1 UUID-backed Contextual GM Notes / Private Vault foundation and adds the first Foundry Source Parity layer for Actor-backed World entries.

The architectural rule is:

> If Foundry knows it, Tome uses it. If Tome adds it, Tome extends it.

For Actor-backed NPC / World entries, the Foundry Actor becomes the canonical source identity. Tome keeps presentation and campaign-extension data, but permanent source identity is UUID-backed and must survive rename, move, reload and multi-client use.

## Blocking gate A — Explicit Actor identity / migration

1. Back up the test world.
2. Start from a world containing existing Actor-backed Tome NPC / World entries.
3. Open Tome as GM and allow qa.2 initialization to finish.
4. Verify linked entries still open normally.
5. Verify existing explicit `sourceUuid`, `sourceDocumentType` and/or legacy `actorId` links resolve to the intended Actor.
6. For a legacy NPC that only has the previous unique-name fallback available, verify qa.2 may use that fallback once to establish the permanent link.
7. Rename or move the Actor after the permanent link exists.
8. Verify Tome continues using the same Actor UUID and does not attempt to relink by name.

**PASS only if Actor-backed entries have one stable canonical Foundry identity after normalization.**

## Blocking gate B — Actor rename -> Tome

1. Open an Actor that is linked to a Tome World NPC.
2. Rename the Actor from the Foundry Actor sheet.
3. Save / close the Actor sheet.
4. Return to Tome.
5. Verify the linked Tome entry now uses the Actor's new name.
6. Reload Foundry and verify the new name remains correct.

Expected: Actor name is canonical for the linked Actor-backed World entry.

## Blocking gate C — Tome rename -> Actor

1. Open the same linked NPC / World entry in Tome.
2. Rename it using the normal Tome authoring workflow.
3. Open the real Foundry Actor.
4. Verify the Actor has the same new name.
5. Reload and verify both sides still agree.

Expected: editing a Foundry-owned field through Tome writes to the real Foundry Actor rather than creating a divergent duplicate value.

## Blocking gate D — Actor image parity + Tome presentation override

### D1 — Follow canonical Actor image

1. Use an Actor-backed World entry whose Tome profile image is still source-managed.
2. Change the Actor image in Foundry.
3. Return to Tome.
4. Verify Tome follows the new Actor image.
5. Reload and verify persistence.

### D2 — Tome-only override

1. Set a different Profile image in Tome.
2. Change the Actor image again in Foundry.
3. Verify the Tome-only presentation override remains unchanged.
4. Verify the underlying Actor image still changes normally.

### D3 — Return to source image

1. Use **Follow Actor image in Tome**.
2. Verify the Tome profile returns to the current Actor image.
3. Change the Actor image again.
4. Verify Tome follows it again.

### D4 — Save to Actor

1. In the Tome source controls, enter a new canonical Actor image path.
2. Use **Save to Actor**.
3. Open the Actor sheet.
4. Verify the real Actor image was updated.

Expected: Foundry owns the canonical Actor image; Tome may explicitly override presentation without silently changing the Actor.

## Blocking gate E — Tome Private Vault <-> Actor-sheet Private Vault

1. Open an Actor-backed NPC in Tome as GM.
2. Add a Private Vault note with obvious test text and save it.
3. Open the real Foundry Actor sheet.
4. Open **Private Vault** from the Actor sheet.
5. Verify the same note is present.
6. Edit the note from the Actor-side vault and save.
7. Return to the Tome entry and reopen Private Vault.
8. Verify the edited note is present.
9. Add a second note from Tome, reload Foundry and verify both access paths still show the same note set.

Expected: the Actor-backed World entry and the real Actor resolve to one logical private context. The qa.1 Journal-keyed record may be retained/mirrored during migration QA, but it must not behave as a separate divergent vault.

## Privacy gate — BLOCKING

1. Log in as GM and open an Actor-backed World entry.
2. Create a Private Vault note containing obvious secret text.
3. Save.
4. Keep a normal Player client connected with permission to view the public entry / Actor where applicable.
5. Verify:
   - no Private Vault control is available to the Player;
   - secret text does not appear anywhere in the Player Tome DOM/UI;
   - secret text does not appear on the Player Actor sheet;
   - ordinary public content remains visible according to existing Foundry/Tome permissions.
6. Repeat with Section Editor and Entry Editor accounts where available.

**PASS only if delegated users never receive/render private note UI or private content.**

## Blocking gate F — Deleted / missing Actor source

1. Choose a linked Actor-backed World entry and note its name / private note content.
2. Delete the underlying Foundry Actor.
3. Return to Tome.
4. Verify the Tome entry remains present.
5. Verify Tome clearly reports that the linked Foundry Actor is missing.
6. Verify the stored source UUID is retained.
7. Create another Actor with the same name.
8. Verify Tome does **not** silently establish a new permanent link by name.
9. Reload and verify the missing-source state remains controlled and the Tome extension/private data has not been destroyed.

Expected: delete-aware, UUID-stable behavior with no dangerous automatic identity replacement.

## Live update / loop safety

Test repeatedly while both Tome and the relevant Actor sheet are open:

- rename Actor;
- rename linked Tome entry;
- change Actor image;
- switch Tome image between source-follow and override;
- add/edit Private Vault notes;
- move Actor and/or helper Journal between folders.

Verify:

- updates settle once;
- no rename or image ping-pong;
- no recurring update storm;
- no duplicate Private Vault notes caused by reconciliation;
- Tome remains responsive.

## qa.1 Private Vault regression

For Actor, Session, Quest, World entry and Rule:

1. Open the Tome detail/context.
2. Verify Private Vault remains GM-only.
3. Add a note.
4. Set Type, Status, Pin, Trigger and optional Target Session.
5. Save.
6. Close/reopen the same context.
7. Verify all values persist.
8. Navigate to another entry and verify its note set is independent.
9. Return to the original and verify data remains attached to that source.

## UUID persistence

For a non-Actor Journal-backed context:

1. Add a private note.
2. Rename the Journal.
3. Move it to another Foundry/Tome folder.
4. Reopen it in Tome.
5. Verify the private note remains attached.

Expected: rename/folder movement does not affect the UUID-backed association.

## Legacy migration

Use a world with existing v1.1.15 GM Notes and/or qa.1 contextual notes.

1. Back up the test world.
2. Upgrade to qa.2.
3. Open Tome as the same GM.
4. Open entries that already contain GM Notes / Private Vault notes.
5. Verify those notes remain present.
6. For an Actor-backed World entry, verify the note is also reachable from the linked Actor-side Private Vault.
7. Edit one note and save.
8. Open the existing GM Notebook/access editor where applicable.
9. Verify the edited note is still present there during the v1.2 compatibility bridge.
10. Reload Foundry and repeat.

Expected: no legacy private note is deleted or overwritten merely by migration/reconciliation.

## Empty/delete behavior

1. Create two private notes on one source.
2. Remove one and save: one remains.
3. Remove the final note and save.
4. Reopen source from both Tome and Actor side when Actor-backed.

Expected: zero-note state is clean and does not generate phantom or resurrected notes.
