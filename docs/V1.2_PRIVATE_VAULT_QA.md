# Adventurer's Tome v1.2.x — Contextual GM Notes / Private Vault QA

## Build under test

- `v1.2.0-qa.1`
- Stable regression baseline: `v1.1.15`
- Foundry baseline: `13.351`

## Scope of qa.1

This first v1.2 QA build introduces the UUID-backed contextual Private Vault foundation while deliberately preserving the existing v1.1 GM Notebook/access-editor storage path as a compatibility bridge.

### New behavior

- GM-only **Private Vault** lock button appears in the Tome top bar when a contextual campaign object is open.
- Supported contexts in qa.1:
  - Character / Actor profile
  - Session
  - Quest
  - World entry (NPC, Location, Faction, Item, Lore and other World categories)
  - Rule entry
- Private notes can be added, edited, removed, pinned and given type/status/trigger/session target directly from the current Tome context.
- New private storage uses the linked Foundry Document UUID as the canonical key.
- Existing `gmPrivateVault` data is imported non-destructively into the UUID vault.
- Writes are mirrored to the legacy vault during v1.2 migration QA so existing Notebook/access workflows continue to see the same note data.
- The new vault remains `scope: user`, preserving the existing per-GM privacy model.

## Privacy gate — BLOCKING

1. Log in as GM and open a World entry.
2. Create a Private Vault note containing obvious secret text.
3. Save.
4. Log in simultaneously as a normal Player who can view the public entry.
5. Verify:
   - no Private Vault lock/control is present for the Player;
   - secret text does not appear anywhere in the Tome DOM/UI;
   - ordinary public entry content remains visible according to existing permissions.
6. Repeat with Section Editor and Entry Editor accounts where available.

**PASS only if delegated users never receive/render private note UI or content.**

## Context workflow

For Actor, Session, Quest, World entry and Rule:

1. Open the Tome detail/context.
2. Verify the lock button appears for GM only.
3. Open the drawer.
4. Add a note.
5. Set Type, Status, Pin, Trigger and optional Target Session.
6. Save.
7. Close/reopen the same context.
8. Verify all values persist.
9. Navigate to another entry and verify its note set is independent.
10. Return to the original and verify data remains attached to that source.

## UUID persistence

1. Add a private note to a Journal-backed entry.
2. Rename the Journal.
3. Move it to another Foundry/Tome folder.
4. Reopen it in Tome.
5. Verify the private note remains attached.

Expected: rename/folder movement does not affect the UUID-backed association.

## Legacy migration

Use a world with existing v1.1.15 GM Notes.

1. Back up the test world.
2. Upgrade to qa.1.
3. Open Tome as the same GM.
4. Open entries that already contain GM Notes.
5. Verify those notes appear in Private Vault context.
6. Edit one through the new contextual drawer and save.
7. Open the existing GM Notebook/access editor.
8. Verify the edited note is still present there.
9. Reload Foundry and repeat.

Expected: no legacy private note is deleted or overwritten merely by migration.

## Empty/delete behavior

1. Create two private notes on one source.
2. Remove one and save: one remains.
3. Remove the final note and save.
4. Reopen source.

Expected: zero-note state is clean and does not generate phantom notes.

## Reload / multi-client

- Save private notes, reload GM client, verify persistence.
- Keep Player client connected while GM creates/edits notes; verify no private UI/content appears on Player client.
- Navigate repeatedly between contextual entries; drawer state must not become attached to the wrong entry.

## Console gate

No recurring Adventurer's Tome errors during:

- opening contextual drawer;
- adding/removing notes;
- saving;
- navigation;
- reload;
- legacy migration.

A safe migration warning is acceptable only if legacy data remains intact and the old workflow still works.

## Promotion criteria for next v1.2 QA increment

`v1.2.0-qa.1` can advance when:

- privacy gate passes;
- legacy migration passes;
- all five contextual source families pass;
- no data-loss regression is found;
- representative v1.1.15 regression remains clean.

The next v1.2 increment should then harden missing/deleted UUID handling, contextual backlinks and broader vault browsing before the v1.2 milestone is considered complete.
