# 1.8.0-qa.1 — Player Chronicle Foundation

Local QA build on the stable 1.7.0 base. Not published, tagged, or merged.

## Included in this build

- Players get **My Chronicle** in the navigation position used by Campaign Tools for GMs.
- Personal notes and bookmarks reference canonical Foundry UUIDs. Entity names are resolved from the visible document; no NPC, location, or other campaign identity is duplicated.
- A note can link several visible entities. Personal sections appear on character, World, Session, Quest, and the generic entity detail surfaces.
- **Share with GM** and **Share with Party** send explicit saved snapshots. Further private edits do not silently change a shared version.
- GMs get **Player Signals**, with the player's original text, selected signal category, timestamp, and visible entity links.
- Optional per-note encryption, explicit locking, withdrawal and deletion.
- **Save as rumour…** stores an unconfirmed GM claim with subject, source UUID, and excerpt. It creates no anonymous Contact and writes no canonical fact or relationship. Saved claims are under Analysis → Saved Rumours. The existing review dismissal/Undo remains separate from the saved claim.
- A nearby, preceding full name can resolve a subsequent first name to a single existing identity. Competing identities, missing offsets, future-only full names, and explicit ambiguity remain in Review. No global first-name alias is learned.

Known-to-Me collections, remembered-moment timelines, unified Chronicle search and advanced Next Session aggregation remain later QA work. Search here covers the notes currently displayed.

## Data and privacy

`adventurers-tome.playerChronicleV1` is a Foundry V13 **user-scoped**, server-persisted setting. It contains the user's private records, explicit shared snapshots (outbox), and received snapshots (inbox). Reusing the same world/user on another computer accesses the same server data. No browser-local database is the authority, and Chronicle does not create JournalEntry notebooks in production.

Plain notes are private **inside Tome**. Server administrators can inspect unencrypted server storage. Optional encryption uses AES-GCM with PBKDF2-SHA-256 (600,000 iterations), a fresh salt and IV, and authenticated world/user/note identifiers. The title, body and links are encrypted together. The passphrase is not persisted. HTTPS or localhost is required for encryption. Lost passphrases are not recoverable. This protects stored ciphertext, not a hostile server delivering modified application code.

Explicit sharing creates a recipient-addressed Foundry whisper containing a generic notification and the shared snapshot in its module flags. Foundry limits the whisper and its flags to the listed recipients; this makes delivery durable if a recipient is offline. On opening Player Signals or My Chronicle, Tome imports snapshots addressed to the current user into that user's own user-scoped inbox. The snapshot remains in chat history until the message is deleted. Shared whispers are visible to their recipients and the Foundry server administrator.

The sender and recipient do not need to be online at the same time. The server-retained whisper is the delivery queue. Once imported, deleting the chat notification does not remove the inbox entry. The sender keeps an outbox copy; private edits never mutate that copy.

Withdrawal sends a tombstone whisper and removes the snapshot from recipients' active Tome inboxes when they next open Tome. Earlier shared whispers remain in chat history until deleted, so withdrawal cannot erase text already delivered or retained there. Recipients may also have copied the text.

Foundry permissions and Tome visibility are checked before presenting entity links and picker choices. Links are also intersected with recipient access at sharing time. Original player-written text is not automatically rewritten or redacted. The player reviews that text before sharing.

Chronicle records and ChatMessage whisper snapshots do not enter Campaign Memory, campaign facts, relations, discovery, the shared index, or shared search. Campaign Index and discovery scan campaign Actors, Items, Journal Entries, and Scenes; ChatMessages are not index sources. Chronicle setting changes do not enqueue campaign analysis. Chronicle panels are excluded from ordinary page-sharing exports.

## Live QA checklist for Per

1. Back up the test world. Install the local module folder and reload GM plus two separate player accounts.
2. Player A: open My Chronicle; save a note linked to an NPC and a Session, with a bookmark. Player B and GM must not see it in their Tome, search, counts or index. Editing it should not start campaign analysis.
3. Open the same player account in a second browser/computer. Confirm the saved note is available. Rename the linked NPC as GM; confirm the link still opens the same identity.
4. Share with GM. Confirm one private whisper, one Player Signal, no Player-B access, and no new campaign facts. Edit privately; the GM must still see the earlier shared version.
5. Share with Party; check visible links as both players. Revoke access to a linked entity and refresh: that entity's link must disappear.
6. Keep the GM offline, share a note from the player, then reconnect only the GM. Open Player Signals and confirm the snapshot imports. Delete the chat whisper after import; the signal should remain in Tome. Withdraw the note and confirm it disappears from Tome after the next import.
7. On HTTPS/localhost, encrypt a note; reload, unlock, try a wrong phrase, and lock again. Verify no title/body/link is shown while locked. Plain-note features remain usable on ordinary HTTP.
8. In Review, save the anonymous traveller's claim as a rumour about the intended person. Confirm provenance under Saved Rumours, no anonymous Contact, no confirmed relationship, and normal review Undo behavior.
9. Check the Oskar context and a deliberately ambiguous two-person first-name case. The first may link; the second must remain a decision.
10. Check Session, Quest, character, World and generic entity Chronicle sections, including scroll/focus while background analysis updates.

## Limits to verify before stable release

- Cross-device **simultaneous** writes are not an atomic compare-and-swap. Same-client writes are queued and stale revisions are rejected, but concurrent server writes from two browsers need live testing; avoid editing the same Chronicle concurrently during qa.1.
- Offline delivery depends on retaining the recipient-addressed whisper until the recipient has imported it. Deleting the whisper before import removes the only queued copy; after import, deleting it does not remove the Tome inbox snapshot. Withdrawal removes the Tome inbox entry but leaves the original whisper history until deleted.
- Verify offline whisper delivery, native whisper permissions, and server-backed user setting synchronization with two real players. The browser harness validates integration logic, not Foundry's server implementation.
- Encryption cannot be tested on an insecure LAN HTTP origin. It deliberately fails closed there without disabling plain notes.
