# 1.9.0-qa.3 — Campaign Memory and owner-aware migration

Local QA build. Stable channel remains 1.8.0. Nothing is published by this delivery.

## GM workflow

Use a new qa.3 export to include account metadata, campaign presentation, group Actors, the exporting GM's Campaign Memory ledgers, private vaults, workspace, reveal queue, their own Chronicle books and their already-shared inbox. No other user's private Chronicle settings are read. Exports remain private GM archives.

Import → Preview Import → map accounts once → Do Import. The exporting GM maps to the currently importing GM. Each remaining account needs either a destination account or an explicit Keep GM-only choice. Names do not automatically grant permissions; account roles are not changed.

Documents are staged GM-only. Original ownership is restored after document creation and private-data restoration. Journal page overrides are restored before their parent is made visible. An unmapped explicit permission prevents widening that document's default visibility. Migrated compendiums stay private; Folder aliases keep existing canonical folders. UUIDs and known Actor/Item ID fields in private settings are remapped.

Existing local private notes are merged, not replaced. Source private settings and old Undo snapshots are retained in the importing GM's user-scoped migration archive. Old destructive Undo commands are not activated against the new world. Setting writes have per-package checkpoints; a stopped import reports its unfinished phase and can resume from the same ZIP. Saved document copies are reused rather than duplicated.

Older schema-1 ZIPs remain importable but contain no GM-private/account section. They continue to create GM-only copies. A new export is required for this step.

## Player workflow

In the old world: My Chronicle → Move my Chronicle → Export my Chronicle.

After GM account mapping, sign in on the mapped account in the new world: My Chronicle → Move my Chronicle → Import my Chronicle, choose the JSON file and campaign migration. No simultaneous GM/player connection is required. The file stays with the player; do not send it to the GM.

Only the importing account's own books are restored. Incoming inbox content is ignored. Existing notes survive collisions; repeated imports of the identical file do not duplicate notes. Saved shared versions are not automatically sent to recipients again. Re-share explicitly when appropriate.

Encrypted note bodies stay encrypted. Their original world/user/note authentication context is retained so the same passphrase works after migration, including collision-renamed note IDs. Link remapping happens after unlock, and target visibility is checked again before showing links. Migration receipts use addressed GM-authored deliveries, then are cached in that player’s user-scoped storage; ordinary User flags are not used. They contain only targets visible to their mapped recipient, no GM private text or Undo archive. Chronicle storage remains outside Campaign Index.

## Live QA

1. New source export → clean target import; map GM and one player. Verify private GM notes, memory, group Actors, links and Foundry ownership/page overrides.
2. Export a player's Chronicle, import on that mapped player account. Verify plain note, bookmark and remembered moment; repeat the same import and verify no duplicates.
3. Unlock an imported encrypted note with its original passphrase. Verify GM Signals contains only explicitly shared versions and private Chronicle notes are absent from Campaign Index.

TAF → Realm Guard testing against the actual live source remains pending until that environment is available. Automated fixture and browser tests do not replace that live check. No automatic repair/deletion of earlier occupied duplicate folder trees or incorrectly imported starter templates is performed.
