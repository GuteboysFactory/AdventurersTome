# v1.7.0-qa.29 — Universal Foundry Backend Folder Parity

**Baseline:** v1.7.0-qa.28  
**Foundry baseline:** V13.351  
**Scope:** lock Foundry as the backend/source of truth for every Tome standard folder and make Tome a synchronized presentation/workflow layer.

## Locked architecture

```text
Foundry Folder / Document
          ↓ authority
canonical Foundry UUID
          ↓
Adventurer's Tome
folder / card / detail / workflow
```

Tome does not own a parallel campaign database.

If a campaign object exists only as a Tome presentation object, that object must identify the canonical Foundry source document. Managed presentation projections are read-only mirrors; the source Foundry document remains authority.

## Standard folder matrix

| Tome area | Canonical Foundry backend |
| --- | --- |
| Sessions | JournalEntry / Journal folders |
| Quests | JournalEntry / Journal folders |
| Rules | JournalEntry / Journal folders |
| World / Contacts | JournalEntry directly; Actor-backed Contacts may project from Actor folders / semantic contacts |
| World / Factions | JournalEntry directly; external Foundry Journal folders may project into the canonical Tome folder |
| World / Items | JournalEntry directly; real Foundry Item folders/items may project into Tome |
| World / Locations | JournalEntry directly; external Foundry Journal folders may project into Tome |
| World / Lore | JournalEntry directly; external Foundry Journal folders may project into Tome |
| World / NPC | Foundry Actor folders / Actor documents when a native Actor backend exists |
| World / NPC Groups | Foundry Actor folder trees when the system/provider stores NPC groups as Actor folders |
| Future standard folders | Foundry Journal-backed by default until a provider declares a native backend |

## Managed projections

Actor, Item, or external Journal content that belongs to a backend folder not directly renderable by Tome's Journal-based World explorer is represented by a managed Journal projection.

The projection stores:

- canonical `sourceUuid`
- canonical source document type/id
- source folder/root identity
- category
- current source folder path
- generated presentation profile

The projection is **not identity authority**. Campaign Identity Reconciliation resolves it back to the canonical source UUID.

## Folder parity

Nested source folders are mirrored into the Tome World tree.

Source-side changes:

- create folder → mirrored in Tome
- rename folder → mirror updates
- move folder → mirror moves
- delete empty folder → mirror disappears
- create/update/move/delete source document → Tome presentation follows

Tome-side changes for managed mirrors are routed back to the canonical source folder where safe:

- create subfolder
- rename mirrored folder
- move mirrored folder
- delete empty mirrored folder
- move a managed projection
- rename a managed projection
- delete a managed projection

Tome never edits the mirror as if it were an independent campaign entity.

## NPC creation

Native and generic NPC creation now receives the canonical backend destination when the Tome folder maps to an Actor backend.

For native providers that complete through callbacks, Tome also normalizes the created Actor into the canonical backend folder before the caller completion callback resolves.

## Presentation safety

Managed backend projections:

- cannot use ordinary World inline editing
- do not expose Journal-page editing/parity controls
- expose the canonical Actor / Item / Journal as the Foundry source action
- preserve source ownership on the presentation projection

## QA — clean world

### A. Existing NPC

1. In Foundry Actors create/use folder `NPC`.
2. Put Actor `Gunther` in it.
3. Reload or run backend parity sync.
4. Open Tome → World → NPC.

Expected:

- Gunther appears in Tome.
- Gunther's canonical identity is the Actor UUID.
- opening the source opens the Actor, not the managed projection Journal.

### B. Direct Foundry lifecycle

Using a new Actor in Foundry `NPC`:

1. Create.
2. Rename.
3. Move into a nested Actor folder.
4. Rename/move the nested folder.
5. Move Actor out of the NPC backend root.
6. Delete Actor.

Expected: Tome follows every operation after the parity refresh. No orphan projection remains.

### C. Empty nested folder

Create an empty nested Actor folder under `NPC`.

Expected: matching nested folder appears in Tome even before it contains an Actor.

### D. Tome folder routing

From Tome World/NPC:

1. Create a subfolder.
2. Rename it.
3. Move it.
4. Delete it while empty.

Expected: the operations occur on the real Foundry Actor folder and Tome mirrors the result.

### E. Tome NPC creation

Create an NPC from Tome in the NPC root and, where available, a mirrored nested NPC folder.

Expected:

- a real Foundry Actor is created
- Actor lands in the canonical backend folder
- Tome renders that Actor through its managed projection

### F. Items

Create a real Foundry Item under an `Items` Item folder.

Expected:

- it appears under Tome World/Items
- canonical Item UUID is authority
- source action opens the Item
- Item rename/move/delete flows back into Tome

### G. Journal-backed folders

Create/rename/move entries directly in canonical Tome/Foundry Journal folders for Sessions, Quests, Rules, Factions, Locations and Lore.

Expected: Tome reflects the real Journal backend with no second database.
