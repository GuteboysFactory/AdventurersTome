# Adventurer's Tome v1.6.0-qa.4 — Privacy Semantics & Semantic Write Contract

**Stable baseline:** v1.5.0  
**Previous USL gates:** qa.1 PASS, qa.2 PASS, qa.3 PASS  
**Verified Foundry baseline:** V13.351

## Goal

Lock privacy semantics and the first semantic write contract together.

qa.4 remains **dry-run only**. It does not call `Document.update()`, create documents, mutate the Private Vault, or execute any semantic write.

## Semantic Catalog v4

New semantics:

- `notes` — privacy container only
- `notes.private` — owner-only
- `notes.gm` — GM-only
- `notes.public` — player-visible / explicitly revealed

The container itself does not flatten mixed-visibility notes into one payload.

## Canonical note ownership

### notes.private

System-owned personal/private character notes when the system has a natural field.

Realm Guard reference mapping:

- semantic: `notes.private`
- source: `system.notes`
- visibility: `owner-only`
- revealState: `private`

### notes.gm

Tome-owned GM-private context.

Canonical source:

- contextual Private Vault v2
- UUID-backed
- GM-only user-scoped storage
- never stored as player-readable Actor flags

Semantic result:

- provider: `tome-private-vault`
- authority: `tome`
- visibility: `gm-only`
- revealState: `hidden`

### notes.public

Tome Known Information / explicitly player-visible information.

Canonical source:

- `flags.adventurers-tome.knownInformation.html`

Semantic result:

- provider: `tome-known-information`
- authority: `tome`
- visibility: `player-visible`
- revealState: `revealed`

## Private Vault API hardening

The contextual Private Vault API adds:

`getNotes(document)`

Behavior:

- GM client → cloned note array
- non-GM client → empty array

No player-facing semantic flow receives Private Vault data.

## Semantic write planning

Public API additions:

- `semantic.canWrite(source, semantic, options?)`
- `semantic.planWrite(source, semantic, proposedValue, options?)`

The write planner is dry-run only.

Example:

    await tome.semantic.planWrite(actor, "goals", "Reach Rivendell")

Expected shape includes:

- allowed
- dryRun = true
- operation
- authority
- provider
- targetUuid
- targetPath
- sourcePath
- visibility
- revealState
- permission
- currentValue
- proposedValue
- conflict
- conflictReason
- writable

No mutation method exists in qa.4.

## Adapter capability

Adapter API v1 gains additive capability:

`semanticWritePlan`

Realm Guard reference write-plan mappings:

- `identity.ancestry` → `system.ancestry`
- `identity.class` → `system.rank`
- `identity.biography` → `system.biography`
- `beliefs` → `system.belief`
- `goals` → `system.goal`
- `instincts` → `system.instinct`
- `notes.private` → `system.notes`

Tome-owned note semantics are planned by Tome Core, not by the Realm Guard adapter.

## Permission redaction rule

A denied write plan must not expose hidden source data or hidden storage metadata.

For denied plans:

- allowed = false
- reason = permission
- currentValue = null
- provider = ""
- targetPath = ""
- sourcePath = ""
- proposedValue = null
- writable = false

Visibility class and required permission may be returned because those are contract metadata, not secret campaign content.

## Conflict detection

`planWrite()` supports optimistic conflict checking through:

    { expectedCurrentValue: ... }

If supplied and it differs from the current canonical value:

- allowed = false
- reason = conflict
- conflict = true
- conflictReason = current-value-mismatch
- no mutation occurs

Authorized users may see current/proposed values in the dry-run plan.
