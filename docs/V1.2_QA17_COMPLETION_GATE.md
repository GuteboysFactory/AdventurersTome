# Adventurer's Tome v1.2.0-qa.17 — Completion Gate

## Purpose

`v1.2.0-qa.17` is the final QA/hardening gate for **v1.2 — Foundry Source Parity I + Contextual Private Vault**.

No new feature work belongs in this build. Only blocking regression or parity fixes discovered by this protocol should be added before v1.2 is closed.

Stable regression baseline: `v1.1.15`  
Previous QA baseline: `v1.2.0-qa.16`  
Foundry baseline: `13.351`

Architecture rule:

> **Foundry Document-backed, Tome-rendered.**

> **If Foundry knows it, Tome uses it. If Tome adds it, Tome extends it.**

---

## Gate 1 — Actor-backed NPC source parity

Use one NPC with a permanent Actor UUID link.

1. Open the NPC in Tome and the real Actor sheet.
2. Rename the Actor in Foundry.
3. Verify Tome updates to the same name.
4. Rename from the Tome canonical-name workflow.
5. Verify the real Actor receives the same name.
6. Change the Actor image while Tome is following source image.
7. Verify Tome follows the new image.
8. Enable/use a deliberate Tome presentation image override.
9. Change the Actor image again.
10. Verify the Tome override remains intact.
11. Return Tome to source-follow mode and verify it follows the current Actor image again.

PASS: one stable Actor identity, no name-based re-link after permanent UUID linkage, no rename/image ping-pong.

## Gate 2 — Known Information live sync

### NPC

1. Open Tome Known Information and the linked NPC sheet together.
2. Type continuously for at least 15 seconds in Tome.
3. Allow multiple autosaves to occur while continuing to type.
4. Verify edit mode stays open and focus is not lost.
5. Verify the Foundry NPC Known Information panel receives the same text.
6. Edit the same content from the NPC sheet.
7. Verify Tome receives the update.

### PC

1. Open a Group PC in Tome and the real Actor sheet.
2. Edit Character Information from the Actor-side extension panel.
3. Verify the Tome profile biography updates.
4. Edit the same information from the Tome profile where supported.
5. Verify both sides settle on the same value.

PC extension-panel presentation is **not a v1.2 blocker** if data integrity/live parity works. UI polish is deferred.

### Item

1. Open a World Item in Tome and the linked Foundry Item.
2. Edit Known Information from the Item-side extension panel.
3. Verify Tome updates.
4. Edit from Tome.
5. Verify the Item-side extension data updates.

Item extension-panel presentation is **not a v1.2 blocker** if data integrity/live parity works. UI polish is deferred.

PASS: canonical source data converges both ways and autosave never terminates active typing.

## Gate 3 — UUID / lifecycle hardening

For a permanently linked Actor-backed World entry:

1. Move the Actor to another Foundry folder.
2. Move the helper Journal to another valid Tome/Foundry folder.
3. Reload Foundry.
4. Verify the same source remains linked.
5. Verify Known Information remains intact.
6. Verify Private Vault context remains attached.
7. Delete the linked Actor in a disposable test case.
8. Verify Tome marks/handles the missing source without destroying Tome extension data.
9. Create a new Actor with the deleted Actor's old name.
10. Verify Tome does **not** silently re-link by name.

PASS: rename-safe, move-safe, reload-safe and delete-aware behavior with permanent UUID identity.

## Gate 4 — Contextual Private Vault

Use one Actor-backed NPC and one ordinary Journal-backed context.

### Actor-backed context

1. Add a distinctive Private Vault note from Tome.
2. Open Private Vault from the linked Actor sheet.
3. Verify the same note exists.
4. Edit it Actor-side.
5. Reopen from Tome and verify the same edited record.
6. Rename and move the Actor.
7. Verify the note remains attached.
8. Reload and verify persistence.

### Journal-backed context

1. Add a Private Vault note to Session, Quest, World Journal or Rule.
2. Rename the Journal.
3. Move it between folders.
4. Reload.
5. Verify the same private context remains attached by stable document identity.

PASS: no divergent vault records and no context drift.

## Gate 5 — Player privacy — BLOCKING

Keep a normal Player client connected.

1. Give the Player normal permitted access to a public Actor/World entry.
2. As GM, add obvious secret text to Private Vault.
3. Verify the Player has no Private Vault control.
4. Verify private note text is absent from the Player Tome UI/DOM.
5. Verify private note text is absent from the Player Actor sheet/UI.
6. Verify ordinary public content remains visible according to Foundry/Tome permissions.
7. Repeat while GM edits/saves the private note.

PASS only if private GM data never becomes player-visible.

## Gate 6 — Multi-client / loop safety

With two GM clients if available, or GM + Player:

1. Keep Tome and linked Foundry sheets open simultaneously.
2. Rename source documents.
3. Edit Known Information repeatedly.
4. Edit Private Vault records.
5. Move the Actor/helper Journal between folders.
6. Navigate away and back in Tome.

Verify:

- updates settle once;
- no repeated render storm;
- no duplicated notes;
- no alternating/ping-pong values;
- no disruptive navigation resets;
- no recurring Adventurer's Tome console errors.

# v1.2 PASS criteria

v1.2 may be closed only when all blocking gates above pass:

- explicit stable source identity;
- Foundry edits propagate to Tome;
- Tome canonical edits propagate to the correct Foundry source;
- Known Information live sync works without terminating active editing;
- UUID-linked Private Vault survives rename/move/reload;
- Player privacy is verified;
- no update/render ping-pong;
- representative v1.1 regression remains clean.

Deferred and explicitly **not blocking v1.2**:

- visual redesign of the PC Known Information extension panel;
- visual redesign of the Item Known Information extension panel.

If qa.17 passes without blocker fixes, the next step is promotion/closure of **v1.2 Foundry Source Parity I + Contextual Private Vault** and handoff to the next roadmap milestone.
