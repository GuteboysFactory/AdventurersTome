# v1.7.0-qa.19 — Confirmed Entity Creation & Canonical Identity

**Baseline:** v1.7.0-qa.18  
**Foundry baseline:** V13.351  
**Scope:** allow an explicitly Confirmed Campaign Intelligence candidate to be created through Tome's existing Quick Create / native provider stack, then record the created canonical UUID.

## Goal

Complete the first controlled write path:

```text
Possible New
→ GM Confirm
→ Create & Link
→ creation preview
→ existing Tome Quick Create / native provider
→ canonical Foundry entity
→ canonical UUID recorded in Campaign Learning
```

Normal Campaign Link writes remain disabled in qa.19.

## Preconditions

Creation is allowed only when:

- the user is GM
- the candidate has an explicit qa.18 `confirmed` decision
- no currently visible canonical campaign entity has the exact same normalized name
- the selected semantic type is supported

If an exact-name canonical entity already exists, creation is blocked and the GM should use **Link Existing**.

## Supported creation types

- Character / NPC → `npc`
- Contact → `contact`
- Location → `location`
- Faction → `faction`
- Item → `item`
- Lore → `lore`

Unknown classifications default to Lore in the preview, but the GM may select another supported type before continuing.

## Reuse of existing Tome creation stack

qa.19 does not create a second creation engine.

It delegates to:

```js
game.modules.get("adventurers-tome").api.folderQuickCreate
```

and therefore keeps:

- native system NPC creation where available
- generic Tome World entry creation for Locations/Factions/Items/Lore/Contacts
- existing folder/bootstrap behavior
- existing creation review forms

The candidate name is prefilled into the delegated creation flow.

## Canonical identity

After successful creation Tome requires a resolvable canonical UUID.

The explicit learning record becomes:

```text
candidate text
→ created target UUID
→ target name
→ target Foundry document type
→ semantic type
```

This is stored in the existing world-scoped Campaign Intelligence learning setting.

## Campaign Analysis UI

A Confirmed candidate now exposes:

- **Create & Link**
- **Link Existing**
- **Reset**

Create & Link opens a small Campaign Intelligence preview where the GM verifies the semantic type before entering the normal Tome/native creation flow.

## Primary QA

Use the existing QA Session with confirmed candidates such as Lady Mereth / Pale Wardens.

### Test A — Generic World entity

1. Confirm a Location/Faction/Item/Lore candidate if needed.
2. Click **Create & Link**.
3. Verify the suggested semantic type.
4. Continue.
5. In the normal Tome Quick Create form, verify the candidate name is already filled in.
6. Create.

Expected:

- correct canonical World folder is used
- a real Journal-backed Tome World entry is created
- Campaign Learning records the created UUID
- after refresh/rescan the candidate is no longer Possible New
- the name becomes an existing campaign identity

### Test B — Character / NPC

1. Confirm a Character/NPC candidate.
2. Click **Create & Link**.
3. Keep Character / NPC.
4. Continue.

Expected:

- Tome delegates to its existing Quick NPC/native system provider
- candidate name is passed as initial name/query
- after actual creation a canonical Actor UUID is recorded
- candidate is no longer Possible New after discovery refresh

### Test C — Duplicate safety

If an exact-name canonical campaign entity already exists:

Expected:

- Create is blocked
- no duplicate document is silently created
- GM is directed to Link Existing

## Public API

```js
const c = game.modules
  .get("adventurers-tome")
  .api.campaignEntityCreation;

c.plan({ text, kind, sourceUuid });
c.apply({ text, kind, sourceUuid, semanticType });
c.audit();
```

## Audit

Expected:

- `healthy = true`
- `gmOnly = true`
- `explicitConfirmRequired = true`
- `duplicateExactNameBlock = true`
- `delegatesToQuickCreate = true`
- `canonicalUuidRequired = true`
- `campaignLearningRecorded = true`
- `campaignLinkWrites = false`

## Safety

qa.19 MUST NOT:

- create from an unconfirmed candidate
- silently create an exact-name duplicate
- bypass existing Tome/native creation contracts
- invent a canonical UUID
- write normal Session/Quest Campaign Links automatically
- auto-create based only on model confidence

## PASS gate

qa.19 passes when an explicitly confirmed candidate can be created through the normal Tome creation stack, the resulting canonical UUID is recorded, future discovery treats it as an existing identity, and duplicate/unconfirmed safeguards hold.
